- Chat AI is split into `src/lib/ai/`: `modes.ts` (the four user modes + legacy id migration), `task-router.ts` (pure per-request classifier, tested), `models.server.ts` (inventory + per-mode candidates, max 3), `providers.server.ts` (endpoints/keys/timeouts), `prompts.server.ts`; `/api/chat` only orchestrates and reports the workflow via X-Vision-Execution/X-Vision-Output headers. Why: each part can fail or change independently and the router never alters the selected mode.
- User preferences live as validated JSON in D1 `user_settings.prefs` (`src/lib/settings.ts`); /api/chat reads them server-side, and Research web search runs in `src/lib/search/search.server.ts` (parallel providers, normalized + de-duplicated). Why: request bodies can't spoof preferences and each search source can fail alone.
- Research reports are stored in D1 `research_documents` (owner-only, server functions in `documents.functions.ts`, not in the generic query layer) and shown as a card linking to /documents/$docId; code output uses `components/chat/code` + `full-screen-code-view`. Why: documents stay permission-checked on the server and renderers stay reusable.
- Continuous-story requests (scenes/chapters/episodes…) skip the task engine and use the pipeline: a validated per-item state outline is required before writing (bounded retries, else the run stops), each part gets its own outline lines, and `plot.ts` tracks object state chronologically. Why: parts written apart can only stay consistent through one shared plan.
- Deep requests with a fixed number of separate deliverables run through `src/lib/ai/deep/engine.ts` (plan → one generation request per task → per-task deterministic + independent-model verification → targeted correction → cross-task final validation → ordered assembly), with state persisted per user+requestId in D1 `deep_executions` for resume and duplicate prevention, and real stages streamed as `vision_status` SSE events. Why: one request per deliverable is verifiable and correctable in isolation, and retries never redo accepted work.
- Deep Thinking Mode logic lives in `src/lib/ai/deep/` (pure, tested); /api/chat runs every other non-media deep request through the bounded pipeline: hidden plan (complex/long) → generate → deterministic validate → independent model review → correct → revalidate/re-review, logging stages as `[chat:deep]` JSON and disclosing any unrun or unresolved checks. Why: deterministic checks plus a separate review beat self-assessment, and loops stay bounded.

- Which workflow a chat message triggers (tool job, project, file export, or written answer) is decided only by pure `src/lib/ai/request-route.ts` (tested in `src/test/request-route.test.ts`); non-Default modes and long pasted briefs always get a written answer. Why: keyword triggers inside long prompts sent requests to the wrong workflow.
- Text models: one chain `TEXT_CHAIN` in `models.server.ts` (Nemotron 3 Super → GPT-OSS 120B Groq → Cloudflare); the Deep pipeline's last correction round uses `fallbackCall` (the fallback-first chain); `src/test/accuracy-benchmark.test.ts` is the repeatable accuracy benchmark. Why: one primary/fallback order and measurable accuracy across task kinds.
- Every provider call goes through `src/lib/ai/rate-limiter.ts` (per-provider RPM window, max concurrency, Retry-After cool-down, circuit breaker; tested) inside `streamFromProvider`, which logs `[ai:call]` telemetry. Why: one place enforces limits for chat, deep engine and jobs alike.

- Enterprise Login (VISION BDI): table `enterprise_attempts`, logic in `cloud/enterprise.server.ts`, domain checks in root `security/identity/domain-verification.ts`. Why: one place for attempt state and checks.
- Explicit instruction rules (word ranges, scripts per part, no-commentary, continuity) are parsed and checked in pure `src/lib/ai/deep/instructions.ts`, attached as optional `RequestAnalysis.instructions`, and fed into the existing validate/correct loop; issues carrying `items` trigger section-only rewrites spliced back, then full revalidation; outputs larger than `DEEP_LIMITS.batchItems` sections are generated, corrected and reviewed in bounded batches/windows with a continuity reference, structural repair is deterministic, and any unreviewed or unwritten part is disclosed. Why: one pipeline, same checks at every size, no hardcoded counts.
- Shared AI reliability helpers are pure in `src/lib/ai/`: `limits.ts` (all budgets), `failures.ts` (failure kinds, bounded jittered retry, safe user messages), `requirements.ts` (mandatory/optional requirement checklist with conflict/impossible marks; unchecked items never count as met), `context.ts` (budgeted history keeping standing instructions, task brief, untrusted-content fencing); tested in `src/test/ai-reliability.test.ts`. Why: one place for limits and honesty rules across chat, deep and jobs.
- Phase-2 reliability wiring: `streamFromProvider` wraps every model call in `withRetry` (failures.ts) so chat, Deep stages, Research and jobs share one bounded retry; Project Memory is enforced in /api/chat via `ai/memory.ts` + `memory.server.ts` (one D1 query for prefs+project; "project" scope adds same-project context and drops personal custom instructions); agent tools run only through `tools/tool-schema.ts` `executeTool` (schemas parsed from each tool's `params`), and tool model calls fence their input as untrusted; `startJob` returns the existing job for a replayed id (attempt 1). Why: helpers are only useful on the real paths.
- Chat requests are classified by `src/lib/ai/content-intent.ts` (deliverable / code / data / general) to add a format addendum; a single deliverable is wrapped server-side in one ````markdown fence (`copy-ready-stream.ts`), rendered by `components/chat/markdown` whose Copy writes clean text (+HTML); `text`/`prompt` fences stay literal. Why: one authoritative copy of each deliverable, no extra model call.
- Private files download via `src/lib/download.ts` (credentialed fetch → blob), never a bare `<a href download>` to an auth endpoint; `/api/artifacts/$artifactId` decides via pure `lib/jobs/artifact-download.ts` with distinct 401/403/404/410/502/500 codes. Why: browser download managers can drop the partitioned session cookie, which Chrome reports as "Needs authorization".
- Plugins: `plugins/manifest.ts` derives the 100 plugins from the format registry (code formats excluded — Coding Mode owns them) and `planPluginSend` decides each send (plugin = target, attachment = source); selections live in user_settings prefs.plugins. Repo analyzers keep one fetcher per provider in `repos/*.server.ts`. Why: the UI can never advertise a capability the registry lacks.
- Default (non-Deep) chat runs as a gated task in /api/chat: typed `vision_task` events from pure `src/lib/ai/task-events.ts` (per-task seq; terminal emitter and client ignore stale/duplicate/after-terminal), catalogue stages only for real operations; collected answer → validate → bounded correction through shared provider priority → Finalizing → answer; `render-scheduler.ts` reveals logical units. Why: truthful status and validated answers while Deep keeps its pipeline.
- Default-chat factual verification is pure `src/lib/ai/factcheck.ts` (prioritized claim extraction incl. non-numeric → cached per-claim search → full-page read via `factcheck.server.ts` `fetchPageText` (SSRF-blocked) → exact passages → deterministic judgement with source quality + domain independence; snippets/stale pages never verify → one correction round → re-verify → scoped claim-linked note); records persist owner-scoped in D1 `claim_checks` keyed by user+reply id, read via `claim-checks.functions.ts`. Why: verification rests on retrieved evidence, never a model agreeing, and stays attached to the right user and reply.
- Conversation reference resolution ("your first response", "the previous answer"), conversation working context (standing instructions, latest correction wins, forget) and artifact-vs-source checks are pure in `src/lib/ai/references.ts` (tested in `src/test/conversation-context.test.ts`); /api/chat attaches the resolved source from the full sent history, and the chat client attaches it to file/tool jobs or answers missing/ambiguous references itself. Why: tools must act on real content, never the reference phrase.
- Default chat runs a bounded generate→validate→correct loop (`AI_LIMITS.defaultCorrections`, total ≤5 attempts, models rotate) whose correction prompt quotes the exact failed checks; required names per item (`instructions.requiredNames`, numbered-list aware via `splitItems`) are checked deterministically; `remarkCallouts` also accepts bare/bold `[!NOTE]` markers. Why: corrections must target real failures and raw markers must never render.

- Chat maths renders through remark-math + KaTeX after `normalizeMath` (`src/lib/math.ts`) converts \( \)/\[ \]/math fences and escapes currency; code is never touched. Why: models emit mixed delimiters and dollar amounts.
- Multi-scene outputs are validated as a whole by `src/lib/ai/deep/plot.ts` (object reuse, worn items, camera vs motion, character state, location transitions) inside `validateCandidate`; calculation requests keep the user's figures (`checkInputs`) and skip web fact-checking. Why: per-scene checks missed cross-scene contradictions, and web pages "corrected" correct maths.
- Offline caching uses vite-plugin-pwa (generateSW, client build only) registered solely from `src/lib/pwa.ts`, which refuses dev, iframes, preview hosts and `?sw=off`; pages are network-first and sign-in/admin/API paths are never cached; saved chats mirror to IndexedDB (`src/lib/idb-cache.ts`) and are cleared on sign-out. Why: fast repeats, no stale code or cached private data.
- Requirement Understanding Engine is pure deterministic `src/lib/ai/requirement-spec.ts` (structured explicit/inferred/optional spec + coverage gaps), injected into every non-media /api/chat system prompt with a `[chat:req]` log; scored by `src/test/requirement-benchmark.test.ts` against frozen `requirement-baseline.ts` on DEV/HOLDOUT/HOLDOUT2 fixtures. Why: requirements are captured before generation with no extra model call, and accuracy stays measurable.
- Multilingual support is centralized in `src/lib/i18n/`: `locales.ts` (16 locale configs: script, direction, fonts, request-language detection kept separate from explicitly requested output languages), `requirements.ts` (per-language lexicons feeding `buildSpec`), `pdf-text.server.ts` (runtime-fetched, worker-cached Noto fonts embedded via @pdf-lib/fontkit, run splitting + minimal RTL bidi; WinAnsi-only PDFs keep built-in fonts). Benchmarks: `multilingual-benchmark.test.ts` (dev + two holdouts vs a frozen pre-multilingual engine copy), exports: `multilingual-files.test.ts`. Why: no language conditionals scattered across the app, and holdout scores stay honest.

- Email verification uses 8-digit codes hashed in D1 `auth_otps`; delivery runs on the Cloudflare gateway Worker (`POST /mail`, Gmail SMTP with SMTP_EMAIL/SMTP_PASSWORD bound from the Cloudflare Secrets Store), and the app calls it with the shared MAIL_TOKEN. Why: mail credentials stay in Cloudflare; codes never stored in plain text.
- Files use private Drive via `cloud/drive.server.ts`, canonical destinations in `drive-layout.ts`, app_config reservations and D1 indexes. Browser exports use `drive-export.ts`; admin-only `/api/storage/drive` initializes folders or migrates legacy artifacts in bounded batches. Why: finals share secure storage while runtime staging and owner-only downloads remain intact.
- Subdirectories may have their own `AGENTS.md`; read `src/lib/sandbox/AGENTS.md` before changing the Long Context Generation store.
