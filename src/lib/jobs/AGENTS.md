# Builder jobs

- Builder jobs (code export, project generation, ZIP analysis) run server-side in `src/lib/jobs/` with pure logic in `src/lib/builder/` and archive safety rules in `security/archive/zip-guard.ts`; state lives in D1 `jobs`/`job_artifacts`, the browser starts a job via `/api/jobs` and polls `/api/jobs/$jobId`, downloads go through owner-only expiring `/api/artifacts/$artifactId`. Why: statuses come from real backend steps, stale running jobs are recovered as failed, and nothing heavy or unsafe runs in the browser.
- Final artifacts use private Google Drive through `artifact-store.server.ts`; D1 chunks are bounded source/runtime staging or legacy reads, never a final-storage fallback. Drive folder/upload reservations live in app_config with pre-generated Google IDs; verified uploads are indexed before completion. Why: retries reuse the same object and missing configuration cannot silently store finals in D1.
- Generated projects are validated statically only (required files, JSON, Babel syntax parse, imports, HTML links, CSS braces) with at most 2 AI repair passes; installs/builds/tests are reported as not run. Why: the Cloudflare runtime cannot run package managers or compilers, and results must never claim a build that did not happen.
- Builder tools run only inside the existing chat: chat-workspace starts jobs and renders `components/job-card` inside the assistant message (status, file tree with file view, downloads); there is no separate Builder page. Why: user requires one chat interface, no extra pages or redirects.
- Natural-language tool requests run as `agent_task` jobs: `jobs/agent.server.ts` plans with a general model (JSON plan, max 6 steps, 1 param repair per step), runs tools from `src/lib/tools/registry.server.ts`, re-opens every output file before saving, and outputs come before user attachments so tools default to the user's files. Pure helpers live in `tools/pure.ts`/`tools/office.ts` (fflate-only XLSX/DOCX/EPUB) and are tested in `src/test/tools.test.ts`. Why: real work runs on the server, tools stay testable and runtime-safe, and real data is never retyped by the AI.
- OCR/image questions and speech-to-text use Cloudflare Workers AI (`tools/ai.server.ts`); video processing and raster image editing are not available on the runtime and are reported as such. Why: no native media engines run on Workers.
- Heavy work (image/video/audio, office documents, SQLite/Parquet/Avro/Shapefile, 7z/RAR archives, e-books, fonts, diagram/TeX rendering, large-file checksums) runs as `runtime_task` jobs on GitHub Actions in the fixed repo `tkdasofficial/vision-runtime` (one-word workflows per worker plus `terminal` as a manual alias of logs and `prompts` for linked prompt series with a locked character/style bible checked verbatim, routed by `src/lib/runtime/workflows.ts`, mirrored by its `registry/workflows.json`, relay pins each job to its workflow; allowlisted ops in its `runtime/operations.py`, mirrored in `src/lib/runtime/operations.ts`). The app dispatches with only job id + operation (`GITHUB_PAT`, server-only); runners authenticate to the gateway Worker's `/runtime/*` relay with GitHub OIDC (repo/workflow/main pinned), claim the job once, and move bytes as D1 `artifact_chunks`; status syncs on poll from D1 `runtime_jobs` with a deadline (TIMED_OUT) and GitHub run checks, and the app re-verifies output size/SHA-256/format before offering the download. Why: no secrets or user files ever reach the public repo, its inputs or logs, and nothing is marked done until the real output is verified.
- Linear barcodes (Code 128/39, EAN-13/8, UPC-A/E) are the inline `barcode` agent tool (`tools/barcode.ts`, bwip-js generic build), validated strictly with check-digit errors instead of auto-fixing. Why: runs on Workers with no runner needed.
- Agent-task recovery: `jobs/checkpoint.ts` (pure, versioned, owner+job-bound, TTL) is written to D1 `jobs.checkpoint` after planning and after each step whose outputs are saved; Retry of a failed/cancelled/timed-out agent_task resumes via `jobs/resume.server.ts` (one-time atomic claim on `jobs.resumed_by`, owner-scoped artifact reload with SHA-256 check, fresh restart if anything is invalid) and superseded workers cannot write checkpoints. Other job types restart from stored inputs. Why: finished steps are never redone or assumed, and no two workers advance one task.
- File formats: `src/lib/formats/inventory.ts` is the single registry (the original 131 entries + canonical formats, signatures, per-target route inline vs runtime op); `formats/convert.ts` holds Worker-safe readers/writers used by the `convert_format`/`format_support` tools; `detectRuntimeOp` dispatches runtime pairs from the same registry, and every runtime op must write its output directly in the runner work dir. Tested in `src/test/formats.test.ts` and the runtime repo's `tests/test_format_ops.py`. Why: capabilities are declared once, routed per operation, and never advertised without a tested implementation.
